# 批准前和批准后各检查一次失效

`compute()` 经 Ontop 读取事实，不能和创建任务处于同一个 MySQL 事务。推理和文件指纹留在事务外。事务内只比对锁定行上的业务前提，不把 R-01 重写成 SQL。第一版运行期间不热更新 Mapping、规则和本体文件，因此文件指纹不在数据库锁的保护范围内。

批准在一个事务内完成。先对 `decision_record` 加排他锁，并确认状态仍是待审批。再按订单、事件的顺序加共享锁，重新比对业务前提。不一致时把决策记录记为已失效，不生成审批记录。一致时写入审批记录，并把决策状态更新为已批准，然后提交。只锁决策记录挡不住其他事务修改订单或事件。

批准提交之后、执行开始之前，事实仍可能变化，所以执行前再检查一次。执行前在事务外重新调用 `compute()` 并重算业务前提哈希。执行事务内再次按同一顺序加锁并比对。不一致时审批状态保持已批准，执行状态记为被阻止，不创建任务。检查没有做完时，不把决策记为失效或被阻止；绑定的订单行或事件行已经不存在时，仍按失效处理。规则应用里的直接类型多于一个时，无法确定事件表中的类型列对应哪一个，批准后的执行记为被阻止。

同一决策的并发审批和执行都先拿 `decision_record` 的排他锁。订单行和事件行的共享锁只固定被比对的事实，锁保持到事务提交。业务是否失效只比较 `precondition_hash`，不比较 `facts_hash`。
