# 快照完整性哈希与业务前提哈希分开

决策记录保存 `compute()` 返回的完整基础事实图，格式为按行排序的 N-Triples。图中含有空白节点时拒绝创建决策记录，不对空白节点做替换。`facts_hash` 是这段已保存文本的 SHA-256，用来发现快照被改动。它不参与业务失效判断。供应商名称、订单金额和其他订单的变化会改变全图，但不应使建议失效。

`precondition_hash` 是业务失效判断用的 SHA-256。它覆盖两类输入。绑定事实是订单状态、订单的供应商、事件是否当前有效、事件影响的供应商、事件的具体类型。语义版本指纹是 Mapping、Ontop 本体、阶段二本体扩展、基础事实查询、R-01、`reasoner/core.py` 的哈希，以及 rdflib 和 owlrl 的版本。代码提交号必填，不进入这枚指纹。创建决策记录时，`reasoner/core.py` 的哈希必须等于该提交中这个文件的哈希，否则拒绝创建。提交号用来找回当时的代码。指纹里的哈希用来判断业务前提是否已经变化。

在能够检出该提交、并安装当时记录的 rdflib 和 owlrl 版本的前提下，用保存的事实快照、本体和规则离线重放，得到同一条规则应用。规则应用记录的是绑定，不是通用 OWL 证明。

第一版不单建证据内容表。快照和三份推理侧原文放在决策记录上。当前基础事实只有十余条三元组，三份原文也很短，一行放得下。证据列不授予更新权限，`facts_hash` 仍能核对快照有没有被改。多条决策之间不按哈希去重。快照大到不适合放在决策记录上时，再考虑按哈希分表。
